# 后端 API 开发规范

以现有后端模板的 Controller → Service → SqlSugar 分层为基础，让调用者能从中文说明中理解接口用途、输入约束和实际结果。新增或修改接口时，同步完成实现与说明；只提取规范或补注释时，保持原有接口行为。

## 开始开发前

1. 读取项目约束、目标框架、依赖、启动注册、相邻 Controller / Service、返回类型和异常处理配置。
2. 确认实际使用的是 HTTP API、Hprose RPC，还是两者同时提供；确认路由、服务注册、鉴权和参数绑定方式。
3. 沿调用链核对实现，再写用途、参数和返回值。信息缺失时说明待确认项，不替业务方编造默认值、单位、成功语义或异常状态码。

使用原模板或同源项目时，按需阅读 [模板事实与适配边界](references/template-conventions.md)。需要编写代码或注释时，阅读 [中文注释与 Hprose 示例](references/chinese-documentation-examples.md)。示例的业务约束只适用于示例接口，应根据目标项目调整。

## 中文说明是交付要求

以下要求覆盖本次新增或修改的接口、相关服务业务方法，以及关键算法。用户明确要求全量补齐时，再扩大到对应范围；发现其他存量缺口时记录位置。

### 对外 API 接口

每个对外 Action 必须有完整的中文 XML 文档注释，包含：

- `<summary>`：描述业务用途、操作对象和主要效果。写“按年级与姓名关键字查询学生分页列表”，不要只重复函数名。
- 每个形参对应一个 `<param name="真实参数名">`：中文说明业务含义，并按实际契约写明必填性、允许为空的含义、取值范围、单位、格式、默认值。参数名与签名严格一致，不能遗漏、错位或沿用改名前的名称。
- `<returns>`：说明实际业务结果及边界。`Task<T>` 要解释 `T` 的内容；布尔值要分别说明 `true`、`false`；查询说明无记录时是空集合、`null` 还是其他结果；文件下载说明文件内容、类型及实际失败结果。
- 存在重要业务规则或副作用时，在 `<remarks>` 中补充；存在明确的调用者可见异常时，用有中文内容的 `<exception cref="...">` 说明触发条件。

补充规则：

- 非泛型 `Task` 的 `<returns>` 说明完成后的效果；`void` 没有返回值，在 `<summary>` 或 `<remarks>` 中说明执行效果，不虚构结果。
- 无参方法无需 `<param>`；泛型方法按需添加中文 `<typeparam>`。声明了 `CancellationToken` 等技术参数也要说明用途。
- DTO、请求对象、响应对象及对外字段必须有中文用途说明；复杂对象除方法参数说明外，还需描述调用者使用的关键字段。
- 参数绑定来源应清楚。新接口按实际输入使用 `[FromQuery]`、`[FromRoute]`、`[FromBody]` 或 `[FromForm]`；修改存量接口时先确认绑定兼容性。
- 返回 HTTP 错误与抛异常不是一回事。只有实现及已注册的处理链支持相应状态码时，才写入 `<response code="...">` 或 `[ProducesResponseType]`。

不接受空的 `<returns></returns>`、`<param>`、`<exception>`，或“参数”“结果”“对象”“异步任务”等无法解释业务的占位说明。`<inheritdoc/>` 只有在被继承文档完整且当前文档链能够正确展示时才可使用。

### 服务层函数及 Hprose

服务层公开业务方法也必须具备中文 `<summary>`、逐项 `<param>` 和 `<returns>`，质量要求与 API 一致，不能仅依赖 Controller 上的说明。

在已经采用 XFrameBack.Web Hprose 的业务服务中：

- 服务类使用 `[Service("服务的中文用途说明")]`，沿用项目已有的服务前缀和注册方式。
- 公开业务服务方法使用 `[Hprose(...)]`，第一个字符串始终说明方法的中文用途。
- **合并写法**：多个参数说明放在一个字符串内，按形参顺序以逗号 `,` 分隔；最后一个字符串为返回值说明，即 `[Hprose("方法用途", "参数1说明,参数2说明", "返回值说明")]`。单项说明内部可用分号，避免与参数分隔逗号混淆。
- **逐项写法**：在方法说明后依次传入多个字符串，每个字符串对应一个参数说明，即 `[Hprose("方法用途", "参数1说明", "参数2说明", ...)]`；按所描述参数在签名中的顺序排列。
- **允许只说明必填参数**：以上两种写法均可省略可选参数的 Hprose 说明，不要求说明数量等于形参数量。必填性以实际调用契约与业务校验为准；保留已说明参数的相对顺序，建议带参数名，防止省略后错位。
- Hprose 说明与 XML 文档的业务含义保持一致。合并写法的返回值说明仍须在 XML `<returns>` 中完整记录；XML `<param>` 始终覆盖全部形参，包括 Hprose 中省略的可选参数。
- 无参方法可只写 `[Hprose("方法的中文用途说明")]`；全部参数均可选时，也可仅保留方法说明，完整输入契约写在 XML 文档中。
- 构造函数、私有辅助方法和框架生命周期方法不标记为 Hprose 业务接口；关键私有算法仍须写中文说明。

合并写法示例，假设 `pID`、`path` 必填，其他参数可选：

```csharp
[Hprose("文件夹添加数据",
    "pID：项目名称；必填,path：文件夹路径；必填",
    "返回值：true 表示保存成功，false 表示未保存")]
```

逐项写法示例：

```csharp
[Hprose("按条件查询学生分页列表",
    "grade：年级 ID；为空时不按年级筛选",
    "keyword：姓名关键字；为空时不按姓名筛选",
    "pageIndex：页码；从 1 开始",
    "pageSize：每页记录数；范围以接口实际校验为准")]
```

这些描述必须与方法实现一致；若实际支持 `0` 表示不分页，必须据实补充。直接传多个字符串是正常写法，也可按项目既有风格使用显式字符串数组，不强制数组。不同版本应核对特性构造与文档展示方式；编写约定不等于框架会自动拆分逗号或生成独立返回值字段。

Hprose 标记可能决定远程暴露范围。用户要求实现双通道业务接口时，同步补齐标记；仅补注释且方法此前未暴露时，先确认其业务定位，避免把内部辅助操作变成远程接口。没有 Hprose 依赖的项目使用完整中文服务注释，不为套用规范安装依赖或改造启动流程。

### 关键算法与业务规则

对分页计算、数据转换、排序与匹配、金额计算、状态迁移、批量操作、并发控制等影响业务正确性的逻辑，写清楚：

1. **目的与依据**：解决什么业务问题，规则或公式来自哪里。
2. **输入与输出**：数据单位、范围、空值、顺序和输出含义。
3. **关键步骤与原因**：在分支、公式、去重、事务、重试或取舍处添加中文块注释，解释为何这样处理。
4. **边界与失败**：零值、空集合、重复记录、精度、溢出、超时、部分失败、回滚或幂等语义，按算法实际涉及的情况说明。
5. **性能影响**：当复杂度、批量规模、查询次数或资源成本会影响使用时，解释约束与选择。

方法总体说明放在 XML 注释中，局部原因写在相关代码旁。说明已实现的保障；不能仅靠注释宣称已有事务、鉴权、稳定排序或幂等性。普通赋值和显而易见的语句无需逐行翻译。

## 模板分层与实现约定

- Controller 负责 HTTP 绑定、传输层校验和响应转换；可复用业务规则、数据访问及事务放在 Service。
- HTTP 与 Hprose 共用同一个业务实现；必要的参数和业务约束在 Service 中也要校验，保证不同入口执行一致的规则。
- 复用已有路由、命名、返回结构和异常机制。原模板直接返回实体、`bool` 或 `PageList<T>`，不能因为存在 `JsonView` 类就统一加外层包装。
- 使用实际生效的分页类型。相同类名可能来自不同命名空间，分页字段、页码起点及 `0` 的含义以调用链为准。
- 沿用当前数据库生命周期。使用模板中的 `IServiceScopeFactory` 时，在方法内创建并释放 scope，取得 `ISqlSugarClient`，在释放前完成所有异步操作，不返回延迟查询或共享到后台任务。
- 多表写入需要原子性时使用项目现有事务方式；说明成功、失败与回滚的实际范围。不要把“影响行数大于零”描述为“全部成功”。
- 新增查询按需要采用真实异步 API、稳定排序和批量关联查询，避免照搬模板中的同步查询包装或逐行查询。

## 让中文说明进入接口文档

当任务要求完善 Swagger / OpenAPI 文档时：

1. 确认项目启用 `<GenerateDocumentationFile>true</GenerateDocumentationFile>`。
2. 检查**实际调用**的 Swagger 注册是否包含 `IncludeXmlComments`，XML 文件路径与当前构建产物相符；DTO 位于其他程序集时，按需包含其 XML。
3. 沿用项目已有注册方式，避免重复注册。只存在未调用的扩展方法，不能证明文档已生效。
4. 在可运行环境中检查相关接口的用途、参数和响应字段是否以中文展示。`<returns>` 不保证自动成为响应结构说明；按实际生成器需要补响应元数据并查看生成结果。

仅创建 Skill 时记录这些约定；不顺带修改模板代码或启动配置。

## 完成检查

- 核对本次全部对外 API 和服务业务方法：用途中文、参数完整且匹配、返回值及边界准确。
- 核对 Hprose 类说明、方法说明和所选参数说明格式：合并写法用逗号分隔且最后一个字符串说明返回值；逐项写法每个字符串说明一个参数。允许仅覆盖必填参数，检查已说明参数的名称与相对顺序，确认没有扩大内部方法的暴露范围。
- 核对关键算法的中文说明是否解释规则、原因和实际边界；返回字段、默认值、异常与代码一致。
- 检查 XML 标签合法性，泛型类型引用、`<` 和 `&` 等使用合法 XML 写法；禁止空标签和生成器残留的 `Desc:` 占位文本。
- 修改 C# 时运行适当的构建或项目检查。构建通过不能证明中文注释完整；若屏蔽了 `CS1591`，尤其需要人工逐项核对。
- 只对涉及行为变化或关键边界的改动补充有价值的验证。纯注释修改不新增业务测试；验证构建和文档展示即可。无法运行的检查如实说明。
